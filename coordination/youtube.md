## Dynamic backlight requirements

1. New videos default to enabled dynamic backlight. The existing toggle remains available; no model call is needed for continuing animation.
2. A dedicated agent configuration tool enables/disables the runtime and adjusts intensity, spread, smoothing, tone, opacity, vibrance and continuous room fill. The agent does not guess frame colors or send one tool call per frame.
3. The local runtime obtains actual visible video pixels, extracts multiple spatial color regions and paints outward gradients weighted by the prevalence of those colors. A blue left edge and orange right edge must remain on their respective sides; a global average is insufficient.
4. Temporal smoothing reduces flicker; dark scenes dim the output. Paused frames hold their corresponding colors. Missing/stale sources fade out with an accurate status instead of substituting a fixed palette.
5. Samples exclude the glow itself and neighboring UI. Manual projector transforms require mapping sample locations back into the video's own coordinates; sampling the transformed bounding rectangle alone creates feedback and contamination.
6. Gradients remain within the native surface domain and exclusions. Moving or resizing the panel carries its light field. Frame data and transient color samples are not written into the persisted scene on every update.
7. Start with a bounded, non-overlapping local sampling loop and measure cost/latency. Downsample before color analysis and smooth/interpolate in the renderer. Generalize the pixel-analysis interface for later media providers.

The current native desktop path uses a sandboxed offscreen official-video renderer and its own CPU frame output, not screen sharing or capture of the app window. One 1920×1080 source per content ID supplies latest JPEG frames with matching spatial colors at a configured maximum of 15 fps. The earlier capturePage prototype is historical. Browser fallback still uses explicit same-studio-tab sharing through getDisplayMedia and Capture Handle verification. No direct stream extraction, browser isolation bypass or protected-content capture support is implied.

## Shared contract

- `ContentKind: 'youtube'`, `YouTubeConfig: { videoId, startSeconds, backlight }` and `YouTubeContent` live in canvas-owned `src/shared/content.ts`.
- `videoId` is a valid 11-character YouTube ID. `startSeconds` is an integer from 0 to 86400. `backlight` defaults to `true` for new content.
- Optional `backlightSettings: { intensity, spread, smoothingMs, toneProfile?, opacity?, vibrance?, roomFill? }` preserves existing v3 scenes, including legacy three-number settings. Canonical defaults are intensity `1`, spread `.18`, smoothing `180`, tone `cinema`, opacity `1`, vibrance `1`, roomFill `0`. Ranges are intensity `0–2`, spread `0.02–0.4`, smoothing `0–1000` whole milliseconds, opacity `0–1`, vibrance `0–2`, roomFill `0–1`. Tone profiles are `cinema`, `vivid`, `soft`, `neutral` (UI label Natural). Types, defaults, limits, validation and pixel-analysis helpers live in `src/shared/backlight.ts`. Only the original three numeric fields are required in a full canonical settings object; new fields remain optional. The briefly proposed binary coverage field was never released and is not supported.
- `state: {}` does not claim an authoritative playback clock. Browser player state stays local; native source readiness/playback/errors belong to the host-owned media source. Neither is an authoritative playback clock in the scene or model context.
- Creation, replacement, attachment and removal use the existing `content.*` commands. The canvas chooses valid intrinsic bounds within boundaries/exclusions, preferring open space but permitting overlap with other panels. New players/transfers count toward the five-asset limit shared with timers and all content on the surface. Replacement and lighting changes do not add an asset. Background artwork remains intact.
- `youtube.backlight: { id, enabled }` changes only the matching YouTube instance's lighting configuration. It does not change the video/start/placement or recreate the player.
- `youtube.backlight.configure: { id, settings?: Partial<BacklightSettings>, enabled?: boolean }` applies one atomic edit. At least one setting or enabled flag is required. It merges existing effective settings, preserving unspecified values and rejecting invalid updates without a partial toggle.
- `content.action` does not control YouTube; its registry `actions` is empty. Playback uses the official player's controls.
- A change to video ID or start time re-cues the embedded video, initially paused and muted. Title-only and lighting changes preserve the mounted player. Opened browser players now persist through surface/view and interaction-mode changes. Synchronized playback between windows is not yet established; the native source implementation must validate its own shared-frame behavior.
- This is additive to schema v3; old scenes without YouTube retain their existing content.

`src/shared/youtube.ts` owns `parseYouTubeInput`, `YOUTUBE_ID`, `YOUTUBE_LIMITS` and embed URL construction. Both UI and agent reuse it. It accepts exact video IDs and known YouTube watch, short-link, embed, shorts and live URLs, preserving supported start timestamps. It rejects unrelated hosts, playlists without a specific video, arbitrary embed HTML and invalid timestamps. Parsing a valid ID does not establish that the video exists or permits embedding.

## Agent tools

`search_youtube({query})` searches a short topic through OpenAI Responses hosted web search with the configured key/model. It introduces no canvas command; the current agent has seventeen tools after retiring set_effect. Search is restricted to YouTube domains. Candidates must come from actual provider URL sources, never generated answer text; known URL forms are canonicalized and deduplicated. Up to five candidates receive bounded official oEmbed metadata checks. Results return `videoId`, canonical `url`, original `sourceUrl`, full bounded `title`, canvas-sized `displayTitle`, optional `channel`, boolean `metadataVerified`, and `playbackVerified:false`. Failed/invalid/timed-out oEmbed lookup retains the grounded URL with metadataVerified:false, channel:null and the honest placeholder `YouTube video <ID> (title unavailable)`. Successful metadata retains its title/channel. Missing metadata does not establish embedding permission or watch-page playback failure. Source metadata is untrusted text, not instructions or executable embed HTML.

For a simple topic request the agent automatically selects a relevant result, reuses the single existing target-surface player through `update_content` or default `display_youtube`, and preserves placement/style. It creates only when needed or explicitly asked for another player; search-only requests list options without placing content. Runtime provenance checks reject invented IDs for display and replacement. User-supplied links/IDs (including supported schemeless/timestamp forms), existing scene videos and prior conversation search results remain usable. Search has240-character queries, at most two unique queries per turn, one hosted call each,20s search/5s metadata deadlines and cancellation. Repeated queries are cached within the turn. No-results/provider failures remain errors. Metadata failure only preserves already-grounded source URLs, never generated answer URLs. User cancellation rejects rather than returning fallback candidates. OpenAI search uses the existing key and normal API usage; no YouTube Data API key is required.

`display_youtube({ surfaceId, video, title, backlight, newPlayer })`:

- `surfaceId` is one of the current room's surface handles.
- `video` is a user-supplied link/ID or exact URL returned by `search_youtube`. A search topic is never passed as a URL.
- `title: null` gives the neutral label “YouTube” for a supplied link; searched videos use the returned `displayTitle`. A user label is not evidence of a fetched title.
- `newPlayer: null/false` reuses exactly one existing YouTube player on the target surface, preserving its ID, bounds and lighting style; if none exists it creates one. `true` explicitly requests an additional/separate player. Multiple existing players require an identified target and `update_content`, or an explicit additional-player request.
- `backlight: null` preserves an existing toggle or defaults to true for a new player; true/false applies an explicit request. Replacement uses the new video timestamp or zero, not the previous source’s start time.
- The strict provider schema requires nullable fields explicitly. Local tool execution applies defaults without another model call.

`set_youtube_backlight({ contentId, enabled })` changes an existing player's glow. Follow-ups use the ID from the accepted scene, without duplicating the player. The existing `update_content` tool accepts a full YouTube config when changing videos; `attach_content` and `remove_content` continue to apply.

`configure_video_backlight({ contentId, enabled, intensity, spread, smoothingMs, toneProfile, opacity, vibrance, roomFill })` changes live-light configuration. All configuration arguments accept null to preserve their current values; at least one must be non-null. `intensity: 1.4` means 140% brightness, `spread: .3` means 30% in the runtime's normalized units, and `smoothingMs: 250` smooths transitions over that timescale. `opacity: .6` is 60% blend strength; `vibrance: 1.5` is 150% color strength. `roomFill: .75` is 75% on a continuous spectrum from normal backlight (`0`) to all-surface illumination (`1`). This expands spatial reach rather than merely changing opacity. Timers and foreground panels, including YouTube, remain masked at every value; the field consumes no asset slots and does not reposition content. The AI chooses Cinema for balanced immersion, Vivid for richer colors, Soft for subdued light, or Natural for source fidelity. Simple tone requests change only the profile; explicit slider requests change only their corresponding values. The tool does not accept raw colors, pixel coordinates, capture handles or permission grants. It issues one `youtube.backlight.configure` command. The runtime handles continuing frame acquisition, edge-aware color integration and rendering.

For full YouTube `update_content` replacement, the strict provider schema requires nullable `backlightSettings`: retain existing custom values, or use null for runtime defaults. A supplied settings object has required nullable `toneProfile`, `opacity`, `vibrance` and `roomFill`: retain explicit values, or use null for legacy/default settings. The adapter omits null optional fields for the canonical runtime. Explicit zero values are preserved. Configuration acceptance alone does not demonstrate visual quality.

### Backlight quality redesign — 2026-10-13

The user's example is a red-dominant interior beside a dark blue video edge. Dominant quadrant color must not override the immediate neighboring edge. The near field should continue that blue edge, with interior influence restricted to gentle distant diffusion. Root renderer work is owned by the canvas task; current visual evidence is tracked in its status note.

The AI selects a tone policy from conversation and supplied/searched metadata. Per-frame brightness adaptation, color blending and temporal response run locally. No pixels are uploaded to the model, and conventional adaptation must not be described as neural inference. This reuses the existing OpenAI agent and command, with no new model or transport.

Research precedents (principles, not vendored source):

- [HyperHDR Infinite Color Engine](https://github.com/awawa-dev/HyperHDR/discussions/1322): floating-point linear-light processing, separate brightness control and continuously interpolated transitions. Applied lesson: avoid repeated rounding, encoded-RGB arithmetic and abrupt luminance jumps.
- [Ambient light for YouTube WebGL renderer](https://github.com/WesselKroos/youtube-ambilight/blob/develop/src/scripts/libs/projector-webgl.js) and [2D renderer](https://github.com/WesselKroos/youtube-ambilight/blob/develop/src/scripts/libs/projector-2d.js): continuous source-image expansion, soft diffusion and layered blending. Applied lesson: build one coherent field rather than independently screen-blending dominant-color spots. The project is MIT licensed; no extension code is copied into the agent.
- [Oklab by Björn Ottosson](https://bottosson.github.io/posts/oklab/): perceptual lightness/chroma operations and interpolation. Applied lesson: control saturation and transition distance without treating encoded RGB distances as perceptually uniform. The root renderer owns implementation and any mathematical attribution.

Acceptance includes the dark-blue-border/red-interior case, corner continuity, darkness, black bars, scene changes, smooth motion between source updates and an actual muted video comparison. Preserve surface masks, other artwork and the video source/placement during style edits. Physical projector color calibration remains a later hardware step.

Completed implementation also estimates broad contour direction/curvature from local image gradients at two depths, smooths that estimate over time, and ramps the outer extension away from the anchored seam. This is bounded color extrapolation with a fallback, not semantic prediction or neural outpainting. The [same-frame video comparison](http://127.0.0.1:5173/tests/backlight-comparison.html?view=output) and [curved synthetic comparison](http://127.0.0.1:5173/tests/contour-extension.html) show the difference without editing the saved room. Root93checks/build and agent62checks/build pass. Both tasks visually inspected actual comparison output; physical hardware remains untested.

All tools use the existing ordered, per-call-ID deduplicated dispatch path. Their replies describe accepted placement, update, movement or backlight configuration. Search-only replies list actual returned metadata/URLs and state that no video was placed. They never turn a model's “it is playing” or “the colors now match” claim into a verified runtime assertion. Tool receipts report `playback.verified: false` and `backlight.captureVerified: false`; actual source/status/colors stay local to the canvas runtime, outside model context.

## Rendering and limits

- **Native path implemented, acceptance limited:** a sandboxed offscreen 1920×1080 Electron source per YouTube content ID uses the official embed and publishes capped 15 fps latest JPEG frames with matching spatial colors. Existing surface, 3D, manual and projector painters consume that source without screen/app-window capture. Silent source delivery/lifecycle/mute/pointer tests and a decoded-image/visible-gradient harness pass. Pointer input maps through the inverse calibrated video plane to the official player. The old desktop capture IPC/preload endpoint has been removed; native bridge errors, subscription cleanup and source-preload isolation are tested. Official YouTube startup reached Ready, paused+muted, with six poster frames and no Play. Actual muted moving YouTube/glow is now verified through the localhost worker in Surface layout and clean same-origin output. Physical projection and additional providers remain unverified.
- **Audio/startup requirement:** new browser/native players start paused and muted, including after source replacement. Default-on backlighting does not imply autoplay. The user is on a Zoom call; no Play testing in their live room.
- Native frame rendering is implemented across surface, 3D, manual and projector outputs through the existing calibrated compositor; muted moving-video acceptance passed in the live studio and clean same-origin output; physical projection remains pending. Browser iframe playback uses **Surface layout** and **manual projector output**.
- **Use player on canvas** opens Surface layout and enables interaction. **Interact with content** / **Arrange panels** switches between playback controls and layout editing. Operator Play/Pause controls below the preview operate the official player; agent placement does not autoplay.
- Browser spatial views show placement previews. Native desktop instead receives source frames from its isolated official-player renderer; it does not attempt to read a cross-origin browser iframe as a texture.
- Dynamic backlight samples real pixels, preserves regional color positions/proportions and paints smoothed gradients clipped to the surface domain and exclusions. The inspector and chat use the same persisted enable/settings fields. No source means no fabricated fixed-color fallback.
- Browser control: **Enable live colors** opens a sharing picker; select this studio tab. A Capture Handle nonce verifies the source, and other tabs/windows/screens are rejected. Sharing persists through view, surface, Arrange/Interact, source/configuration and backlight changes. **Stop colors**, removing the final opened player, closing/reloading the page or development teardown releases it. The stop control remains available when the backlight is off. Browser support requires tab sharing and Capture Handle. The native desktop frame source is independent of browser sharing and follows content ID/host lifetime.
- Native source frames are capped at 15 fps; the new analyzer downsamples the entire picture to 192 × 108 and integrates 100 fixed zones: 50 narrow edge samples and 50 broader samples. Color processing uses floating-point linear light, perceptual chroma control, bounded highlights and continuous receiver interpolation on a 33 ms tick. The field uses normalized diffusion and a linear-light compositor; it no longer paints independent dominant-color blobs. Browser iframe capture remains a separate fallback. Sampling/analysis cost is not total projector latency.
- Small-video update owned by the canvas task: the official iframe uses a1920×1080 internal viewport scaled into the projected panel; preview CSS size does not veto playback. Operator Play/Pause/status controls live outside the mapped pixels. YouTube's internal viewport requirement is separate from the size of the video within a physical projector's output. Physical resolution depends on output mapping and hardware, not the browser panel's CSS size.
- A placed player can still encounter network errors, unavailable/private videos, disabled embedding or browser playback restrictions. Those are displayed by the player rather than presented as successful playback.
- No YouTube Data API key is needed for a supplied link or the OpenAI-backed search tool. Native windows consume the host-owned source; moving-video timing/presentation synchronization is not yet verified. Browser windows retain independent playback. Metadata availability does not guarantee successful embedding, exact duration or ad-free playback.

The official [YouTube IFrame API](https://developers.google.com/youtube/iframe_api_reference) documents player size, event/error reporting, client identity and autoplay behavior. The [player parameters reference](https://developers.google.com/youtube/player_parameters) covers the official embed settings.
